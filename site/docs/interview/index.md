## 这个站的三条写作规矩

写的时候给自己定了三条硬规矩，也算是这个项目的"验收标准"：

### 1. 只写代码里能找到的东西

每条结论都能指到具体文件、函数、配置字段或运行日志。

**反面做法**：为了显得厉害，写"基于自研的深度学习模型做了语义理解"——实际就是 `difflib.SequenceMatcher`。这种话一追问就穿。

### 2. 不夸大完成度

| 真实状态 | 就这么写 |
| --- | --- |
| 只有设计文档 | 设计阶段 |
| 能跑但没有部署 | 原型 |
| 在 git 工作树里没合并 | 开发中未合并 |
| 是模板站不是产品站 | 模板站形态 |
| 是工具集不是平台 | 工具链 |

### 3. 把坑和边界一起写出来

每个项目都有「已知边界」一节，写清楚：

- 哪些功能没做完
- 哪些设计有缺陷
- 哪些地方偷懒了
- 如果重做会改什么

::: tip 为什么这么写
面试时**主动承认局限，比假装完美更可信**。

原因很简单：只有真正跑过生产系统的人，才能说出"搜狐成功率只有 69%"这种细节。编不出来。

而且承认短板时如果能同时给出改进方案，反而展示的是**判断力**——你知道什么是好的，只是当时优先级没到。
:::

## 关于"真实状态"这个字段

九个项目里有几个的真实状态和听起来有差距：

| 项目 | 听起来 | 实际 |
| --- | --- | --- |
| RPA | 自动化**平台** | **工具链**，两个独立脚本，无编排无调度 |
| AI 客服 | 智能客服**系统** | 可运行**原型**，未上线，集团版未合并 |
| 合规官网 | 合规**官网** | **模板站**，三套风格可演示 |
| 亿企代账自动化 | 自动化**导入** | CDP 验证通过，**编排层未完成** |
| 做账工具 | 支持 8 种语言 | 实际 **11 种**（文档写错了） |

**这些差距我在每一页都写清楚了。** 如果你是从这里开始看的，建议先扫一遍 [诚实边界清单](/interview/boundaries)。
