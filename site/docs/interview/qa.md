# 高频追问与应答

这一页列的是**最容易被问穿**的问题，以及我的回答。分五类：项目真实性、技术深度、设计决策、失败与局限、工程素养。

## 一、"这个真的做了吗？"

### Q：你说支持 11 种语言，但 README 写的是 8 种？

::: tip 答
代码里 `i18n.py` 的 `LOCALES` 确实是 11 个键：`en / de / fr / es / it / nl / sv / pt / pl / ja / tr`。

README 和开发者文档写 8 种是**文档没跟上代码**，而且文档里列的 `cs`（捷克语）代码里根本不存在，代码反而多了 `pt / ja / tr`。

这是我的疏忽，应该改。而且这个疏忽有实际风险——如果有人信了"支持捷克语"去处理捷克站点，系统不会报错，会用错误 locale 解析然后输出**看起来正常但数字错位**的 Excel。**静默的错误数据比崩溃危险。**
:::

### Q：你这个 RPA 能叫"平台"吗？

::: tip 答
严格说不能，我现在叫它"工具链"。

它是两个各自独立的交付物：一个运单标识脚本、一个物流对账服务。之间没有统一任务编排、没有调度器、没有共享控制台、没有配置化多任务。加一个新任务要写新的 Playwright 脚本，非技术同学用不了。

要成为平台至少得补四样：任务注册表（声明式定义）、统一调度（cron + 并发控制）、状态与审计（每次运行的输入输出）、控制台（非技术同学能操作）。这些我心里有数，当时业务优先级没到那一步。
:::

### Q：AI 客服上线了吗？

::: tip 答
没有。可运行原型完成了——后端、网页挂件、管理后台、WhatsApp 接入、压测脚本都有，但没有 Dockerfile、没有部署配置。

集团多业务线统一版在独立的 git 工作树里，有多次提交但**还没合并回 main**，而且有未提交改动。

另外澄清一点：所谓 unified group AI customer service 的 **group 是"集团/多业务线"，不是微信群**——系统没有企微群接入代码。
:::

### Q：合规官网是上线产品吗？

::: tip 答
是模板站形态，用来选型和演示的。三套视觉风格、咨询面板、模板切换器、内嵌 AI 客服，都能构建能演示，但我没有独立生产部署的证据。

它和云仓官网技术栈同构，是从主站规划里独立拆出来的。
:::

## 二、技术深度

### Q：PDF 没有表格结构，你怎么还原的？跨页怎么办？

::: tip 答
用 PyMuPDF 的 `get_text("dict")` 拿到每个文本片段的 bbox，按 x 坐标聚类识别栏、按 y 坐标聚类识别行。

跨页不是问题——逐页提取后合并 span 列表，天然连续。

真正的难点是**行漂移**。同一行的科目名和金额 y 坐标不一定相等，所以我用固定 7px 的高度窗口做行分组。但日文 PDF 的金额整体下漂 11–12px，会落进下一行窗口，产生孤立的金额。这个我单独加了一层"孤儿金额再分配"，向上找最近的同名科目行归并。

**关键是分层**：7px 窗口是通用规则，孤儿再分配是日文特例。我没有把窗口调大到 15px 去顺便解决日文——那样会让其他语言的行粘连。
:::

### Q：为什么用关键词打分做语言检测，不用分类器？

::: tip 答
因为**可调试性比准确率更重要**，在这个场景里。

关键词打分的结果是可解释的：检测错了，打印分数表就知道哪个词没命中，加个词就修好了。分类器可能更准，但错了没法排查。

财务场景里，"能快速定位并修复"比"平均准确率高一两个点"值钱。
:::

### Q：视频拖动进度条是你实现的 Range 请求吗？

::: tip 答
功能能用，但**不是我实现的**，是 Starlette `FileResponse` 的原生能力。

代码里那个自定义的 `file_iterator` 函数是死代码，没被调用，而且注释里自己都写了 "For proper Range support, use FileResponse instead"。

我的判断是**用对框架能力比自己写更正确**——自己实现 Range 解析要处理多段区间、边界条件、并发，收益为零。但我应该把那段死代码删掉，留着会误导人。
:::

### Q：爬虫绕过验证码，这个你怎么看？

::: danger 答
这是**风险项不是加分项**，我主动说明。

商务部归类模块的代码注释里写了 "MOFCOM tax search with captcha bypass"，是早期为了打通数据源做的权宜之计。

正确做法是走官方 API 或购买数据授权。这个项目当时的定位是快速验证需求，所以选了抓取这条路；如果业务验证成立，下一步必然是数据本地化。

**试图掩饰这个只会更糟。**
:::

## 三、设计决策

### Q：你做了 RAG 又砍掉，是不是其实没做完？

::: tip 答
不是没做完，是**判断这个场景不需要**。

客服知识库的特征是：人工精炼过的、总量有限的、要求准确可预期的。这种情况下把全部知识直接给模型，比让向量检索去猜"哪段相关"更可控。

RAG 在这里的真实问题是**错误静默**——检索到错的片段，模型照样基于它生成，看不出问题。而且答错之后排查困难：是知识没写？切分不对？检索偏了？还是模型问题？四选一。

全量上下文只有两种可能：知识写错了，或者模型理解错了。

顺带说一句我的观察：**大部分"RAG 效果不好"其实不是检索算法的问题，是知识没整理好。**
:::

### Q：品牌词超过 12 次就拦截，为什么？

::: tip 答
因为**过度自我推销的内容会被 AI 判定为广告而拒绝引用**。

AI 搜索要给用户客观答案，不是广告文案。品牌词密度是判断内容性质的强信号。

这条规则反直觉的地方在于：做内容的人本能地想多提品牌，系统反过来限制你。**好系统应该对抗人的直觉偏差，而不是顺从它。**
:::

### Q：无来源的数字为什么不直接删掉？

::: tip 答
删掉会让文章变得空洞、没有信息量，反而不被 AI 引用。

所以是**降级不是删除**——把"3 天送达"换成"具体时效以实际合同为准"，把"成本降低 40%"换成"实际成本因方案而异"。

这样保留话题完整性的同时，规避两重风险：虚假宣传的合规风险，加上 AI 判定无来源数字不可信。

**这不是 censorship，是 risk rephrasing。**
:::

### Q：为什么不每天全自动发布？

::: tip 答
主链路 `run_daily.bat` 默认带 `--skip-publish`，发布环节保留人工确认。

原因是**商业内容发出去收不回来**。生成可以自动化，发布这道闸门得留给人。

另外发布侧也做了三层限流：每日上限 3 篇、单平台上限 2 篇、最小间隔 120 分钟。最小间隔那条是**防封号设计**——短时间密集发布是最典型的被判定机器行为的模式。
:::

## 四、失败与局限

### Q：发布成功率只有 80%，是不是系统不行？

::: tip 答
80% 恰恰是真实系统的样子。

如果一个系统对外发布成功率是 100%，通常意味着它跑的次数太少还没遇到失败，或者它把失败静默吞掉了。

**能测出"搜狐只有 69%"这个结论，说明系统真的跑得够久、记录得够全。** 而且这个数据驱动了后续决策——给搜狐做了专门的"中性行业观察"变体改造，删品牌、删数字、删表格、删链接，适配它更严的审核。

50 天里 24 次失败，每一次都有可操作记录，这比假装 100% 成功有用。
:::

### Q：AI 收录率在下降，你的 GEO 有用吗？

::: tip 答
报告里如实写了趋势：早期 22.6% → 近期 4.8%，下降。爬虫侧也显示 OAI-SearchBot、GPTBot、ClaudeBot 这些还没命中正文，只有 Googlebot 和 bingbot 有文章级命中。

我的看法是：**结构化标记、canonical 策略、llms.txt 这些都是长期资产**，做好了等爬虫来。

但更重要的是——**我能测到它在下降**。如果没有主动探针和日志核验这两条观测链路，我根本不知道效果变差，还以为一切正常。

**"我能测到它没抓到"本身就是能力证明。**
:::

### Q：RPA 没有幂等，重跑会重复打标吧？

::: tip 答
对，**这是个真实的缺陷**，我没做。

工具 A 没有"这条运单是否已标识"的前置查询，重跑确实可能重复打标。正确做法是操作前先查目标状态，已处理则跳过；或者维护一张 processed 表。

同样缺失的还有重试机制、断点续跑、持久化审计、定时调度。

补法我心里有数：网络类异常做指数退避重试、每处理 N 条写一次 checkpoint、任务状态落 SQLite 或 JSONL、用 APScheduler 统一编排加超时告警。

**承认短板加给出路径，比假装没短板强。**
:::

### Q：这些项目有测试吗？

::: tip 答
不均匀，我如实说：

| 项目 | 测试情况 |

| 做账工具 | ✅ 12 国真实 PDF 回归 + SaaS E2E + 亿企代账 8 项单测 |

这是真实的短板。如果要排优先级，我会先给美鸥天眼补后端测试——它依赖外部站点，最容易悄悄坏掉。
:::

## 五、工程素养

### Q：自动化脚本要改真实业务数据，你怎么保证不出事？

::: tip 答
五层：

1. **默认 dry-run**，而且 dry-run 走完整流程——登录、搜索、打开弹窗、填参数、截图，只在最后一次点击前停住。很多 dry-run 实现是碰到写操作就 return，那样只有写操作没被验证。暴露问题才是 dry-run 的价值。
2. **只读优先**，对账机器人对 TMS 只做读，输出差异报告交人工，不自动修正。对账是发现问题的动作，不是修正数据的动作。
3. **幂等与指纹**，做账工具用 sha256 阻止重复入账，全零批次直接跳过不产物。
4. **路径与凭证安全**，文件名服务端 UUID 生成不参与路径拼接，凭证走环境变量，容器非 root。
5. **权限表现一致**，无权限返回 404 不是 403，避免泄露资源存在性。

然后补一句：**工具 A 没做幂等，这是缺陷。**
:::

### Q：发布到别人的平台，你怎么保证不重发不漏发？

::: tip 答
四个能力：

- **幂等**：`content_id + platform` 做键，发布前 `already_published()` 检查。日志里有 **14 次真实跳过**，说明重跑是常态。
- **状态分离**：`public_visible` / `draft_saved` / `unverified` / `failed` 四个状态。现在很多平台"发布"和"存草稿"返回值都是成功，不回访验证你会以为 30 篇都发了，实际 8 篇在草稿箱。
- **有界重试**：候选被拒后**换下一个候选**而不是重试同一篇——被拒通常说明选题不行，重试大概率还是不过。池子耗尽留 `failed_no_candidates`，含每条拒绝原因，并返回非 0 退出码。
- **限流**：每日 3 篇、单平台 2 篇、最小间隔 120 分钟、时段 9–21 点。

**核心思路：外部系统不可靠是前提，不是意外。**
:::

### Q：你的文档和代码不一致，怎么改进？

::: tip 答
这个问题问到了我的痛点。做账工具的 README 写 8 种语言，代码是 11 种。

我的改进方案：

1. **把关键数字从文档改成自动生成**——语言数量、币种数量这些从代码常量里读出来写进文档，不手写
2. **加 CI 检查**——文档里声明的能力，必须有对应的代码常量或测试
3. **文档纳入 review**——改代码时同步检查相关文档

更根本的是认知：**文档是系统的一部分。文档错了，系统行为就不可预期。** 尤其在财务场景里。
:::

## 最后：如果只能记住一句

> **承认局限并给出改进路径，比假装完美更有说服力。**

因为只有真正跑过生产系统的人，才能说出"搜狐成功率只有 69%""工具 A 没做幂等""RAG 我砍了因为不需要"这种话。

这些是编不出来的。
