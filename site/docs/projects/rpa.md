# RPA 自动化工具链

> 运单标识 + 物流对账。用浏览器自动化替代人工在后台系统里的重复操作。

| | |
| --- | --- |
| **业务域** | 海外仓作业 / 物流财务 |
| **技术栈** | Playwright / AutoHotkey / FastAPI / pandas |
| **代码位置** | `RPA/RPA project/zz/nextsls-wecom-rpa/`、`project-codex/rpa_bot/` |
| **真实状态** | 已交付并真实运行，**但它是"工具链"不是"平台"** |

::: warning 先说清楚：它不够格叫"平台"
这是两个**各自独立的**交付物：

| 工具 | 形态 |
| --- | --- |
| 工具 A：运单标识 | 单任务配置驱动脚本 |
| 工具 B：物流对账 | 单场景 API 服务 |

两者之间**没有统一任务编排、没有调度器、没有共享控制台、没有配置化多任务**。

建议表述为「跨境电商 RPA 自动化工具链（运单标识 + 物流对账）」。写"平台"会在追问编排能力时翻车。
:::

## 一、工具 A：运单标识

### 业务痛点

海外仓收到客户发来的运单号清单（通过企业微信），需要在仓储系统里**逐单搜索、勾选标识**。人工做法：下载群文件 → 打开仓储后台 → 一个号一个号搜 → 勾选 → 下一个。

### 实现

| 环节 | 技术 |
| --- | --- |
| 从企业微信取文件 | **AutoHotkey**（`wecom-download.ahk`） |
| 解析运单号 | Node 读 Excel |
| 仓储系统操作 | **Playwright**（仓储系统后台，域名已脱敏） |

::: tip 为什么用 AHK 而不是 API
企业微信桌面端**没有稳定公开的群文件下载 API**。代码注释明确写了这一点。

AHK 脚本靠**屏幕坐标点击**（`Click, 520, 520`），README 也写明"首次使用需按分辨率微调坐标"。

**首次使用按目标分辨率微调坐标**——AHK 段是这套自动化里最值得被记住的实现选择。
:::

### dry-run 安全设计

这是工具 A 最值得讲的部分，因为它要**动真实仓储系统的写操作**。

```json
// config.json —— 默认不写
"behavior": { "dryRun": true }
```

`executeMark(page, dryRun)` 在 dry-run 模式下：

1. 正常打开标识弹窗
2. **跳过"执行"按钮的点击**
3. 按 `Escape` 关闭弹窗

流程上强制先跑 `npm run rpa:dry` 演练、确认截图无误，再跑 `run-real.ps1`。

凭证走环境变量 `WAREHOUSE_USERNAME` / `WAREHOUSE_PASSWORD`，不写死在代码里。

每单搜索和标识前都会**截图存证**到 `artifacts/screenshots/`。

## 二、工具 B：物流对账机器人

### 业务痛点

多家物流商的月结账单，要和 TMS 系统里的供应商流水**逐行核对金额与费用类型**。人工对账枯燥且容易漏。

### 实现

| 层 | 说明 |
| --- | --- |
| 服务 | FastAPI（`main.py`） |
| 对账引擎 | `reconcile_engine.py` |
| 企微对接 | `wecom_crypto.py` 回调解密 |
| 触发方式 | 企业微信回调被动触发，或人工上传 |
| 部署 | Docker + Uvicorn |

对账结果是四分类：

| 标记 | 含义 |
| --- | --- |
| ✅ | 一致 |
| ❌ | 金额不符 |
| ⚠️ | 费用类型不匹配 |
| ⚠️ | TMS 无此运单 |

`data/` 目录下留有某物流商 A（5 月）、某物流商 B（6 月）账单及 `_对账完成.xlsx` 产出，**证明这套流程真实跑过**。

### 安全姿态

工具 B 对 TMS 系统是**只读**的——只做 `fill` / 点击搜索 / 读取表格，不写任何数据。写操作只发生在本地生成 Excel。

::: tip 这是刻意的设计
对账是"发现问题"的动作，不应该顺手"修正数据"。金额不符的记录要交给人工复核，脚本自动改账是灾难。

**只读 + 输出差异报告**，比"全自动修正"安全得多。
:::

## 四、产品哲学：从工具到平台

加一个新任务的标准：**能不能让不懂代码的人加？** 现在不能——加一个任务要写新的 Playwright 脚本、配新的 config、改运行入口。

要成为平台，至少需要：

1. **任务注册表**——声明式定义任务（选择器、步骤、参数）
2. **统一调度**——cron 表达式、并发控制、超时
3. **状态与审计**——每次运行的输入、输出、耗时、失败原因
4. **控制台**——非技术同学能看状态、能重跑、能改参数

这四项是这条工具链下一阶段的演进方向。

## 五、路线图

| 阶段 | 目标 | 关键动作 | 状态 |
| --- | --- | --- | --- |
| 近期 | 幂等与留证 | 工具 A 加「已处理」集合 / processed 表；异常分支也截图留证 | 已立项 |
| 近期 | 审计持久化 | 工具 B 任务状态落 SQLite / JSONL，进程重启不丢 | 已立项 |
| 中期 | 统一编排 | 用 APScheduler / cron 统一调度；失败指数退避重试 | 已规划 |
| 远期 | 控制台 | 非技术同学能看到状态、能重跑、能改参数；AHK 坐标点击替换为可配置元素定位 | 设计中 |

::: tip 推进顺序
先补幂等、审计、重试这些**底座**，再做编排和调度。底座就绪后，调度跑起来才更可靠。
:::

## 六、三十秒版本

> 两套自动化。第一套是运单标识：客户通过企业微信发来运单号清单，原来要人工在仓储后台逐个搜索勾选，现在脚本自动完成。企业微信那一段没有公开的群文件下载 API，所以用 AutoHotkey 做桌面自动化；仓储系统那一段用 Playwright。
>
> 安全上最关键的是 dry-run 设计。这脚本要动真实业务数据，所以默认配置就是 dry-run——它会走完整流程、打开标识弹窗、截图，但跳过最后那一次"执行"点击。必须人工确认演练截图没问题，才能切到真实模式。凭证走环境变量。
>
> 第二套是物流对账机器人，接收企微发来的账单 Excel，登录 TMS 逐单搜索，比对金额和费用类型，输出四分类差异报告。这套对 TMS 是只读的——对账是发现问题的动作，不该顺手改数据，金额不符要交人工复核。
>
> 演进方向是从工具链往平台走：补任务注册表、统一调度、状态审计、控制台，让非技术同学也能加新任务。
