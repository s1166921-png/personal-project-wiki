# 美鸥天眼 · 全球关税与 HS 编码查询

> 打通中国 HS 编码、英国与欧盟 TARIC、美国 HTS、商务部税费库，网页端与微信小程序共用一个后端。

| | |
| --- | --- |
| **业务域** | 跨境通关与合规 |
| **技术栈** | FastAPI / httpx / BeautifulSoup / aiosqlite / React + TS / Taro 4 小程序 |
| **代码位置** | `project-codex/hscode-app/`、`project-codex/hscode-miniapp/` |
| **真实状态** | 已交付，但**数据源依赖外部站点**，且后端缺少测试与文档 |

## 一、它解决什么问题

HS 编码（Harmonized System）是跨境出口报关的核心——一个商品对应一个 HS 码，这个码直接决定关税税率和**出口退税率**。

现实情况是数据散落在四方：

| 数据 | 官方来源 |
| --- | --- |
| 中国 HS 编码、退税率 | 第三方查询站 |
| 英国关税 | 英国 TARIC |
| 欧盟关税 | 欧盟 TARIC |
| 美国关税（含 301 条款） | 美国 HTS |
| 各国税费概览、中外编码对照、监管条件 | 商务部 |

报关员原来的做法是**在这几个站之间来回切**，查一个商品要开五六个页面。这个系统把四方数据聚合到一个入口，网页端和微信小程序"美鸥天眼"都能用。

## 二、架构

```text
┌─────────────┐   ┌──────────────────┐
│  React 网页端 │   │ Taro 微信小程序端 │
└──────┬──────┘   └────────┬─────────┘
       │   同一个 API 后端   │
       └─────────┬─────────┘
                 ↓
        FastAPI（httpx + BeautifulSoup）
                 ↓
       ┌─────────┼─────────┬──────────┐
       ↓         ↓         ↓          ↓
   中国HS编码  英国TARIC  欧盟TARIC  美国HTS / 商务部
                 ↓
       两级缓存：内存 LRU + SQLite
```

**单后端、双客户端**——小程序 `API_BASE` 直接指向同一个 API 域名，调用的 `/hs/search`、`/uk/...` 就是网页端那套接口。不是两套实现。

### 技术选型

| 层 | 选型 |
| --- | --- |
| 后端 | FastAPI + httpx（异步抓取）+ BeautifulSoup(lxml) |
| 缓存 | 内存 LRU + SQLite 持久化，`aiosqlite` |
| 网页端 | React + TypeScript + Vite |
| 小程序 | **Taro 4.0.8**（React 语法编译到微信小程序 + H5） |

选 Taro 而不是原生小程序开发，是为了**用 React 语法写一套代码同时产出小程序和 H5**，和网页端共享组件思路。

## 三、数据来源与缓存

::: warning 一个必须说清楚的点
**系统没有内置 HS 编码数据集。** 所有数据都是**按需实时抓取**上游站点后缓存。

- 搜索缓存 TTL：24 小时
- 详情缓存 TTL：7 天
- 存储：SQLite `cache.db`

所以不要写成"内置 X 万条 HS 编码库"——那是编的。真实形态是**聚合式实时查询 + 两级缓存**。
:::

### 查询实现

| 接口 | 行为 |
| --- | --- |
| `GET /api/hs/search?q=` | 把关键词直接转给上游站搜索 |
| `GET /api/hs/hscode/{code}` | 校验 4–13 位数字、去点去空格，再解析 HTML 表格 |

**没有自研中文分词或语义匹配**——模糊搜索能力完全来自上游站。这是这个项目的真实边界。

详情解析用 BeautifulSoup 抓 HTML 表格（td-label / td-txt 映射），抽取出口退税率、最惠国税率、增值税率、监管条件、申报要素、CIQ 等，并处理两个细节：

- `[过期]` / `[废止]` 状态标记
- 剔除 `display:none` 的隐藏英文 span，只保留中文品名

## 四、技术难点

### 4.1 HS 层级结构

HS 编码是树形的：章（2 位）→ 品目（4 位）→ 子目（6 位及以下）。

| 数据源 | 层级实现 |
| --- | --- |
| 商务部归类树 | `parent_code=0` → 章；`84` → 品目；`8471` → 子目 |
| 英国 / 欧盟 | 详情带 `ancestors` 链：Section → Chapter → Heading |

### 4.2 多语言品名

`translations.py` 是一张大查表，把英/欧/美的关税术语、国名、HS 类标题译成中文。商品描述原文附 `[英文]` 标签保留。

**不是机翻**，是人工维护的术语对照表——关税术语翻错了会导致归类错误，这个领域不接受概率性输出。

### 4.3 退税率联动

`HSCodeDetail` 模型里 `export_rebate_rate` 是独立字段。退税率是跨境出口最直接的经济利益，查询时和关税率并列展示。

### 4.4 反爬健壮性

上游是别人的网站，得讲礼貌也要讲韧性：

| 措施 | 实现 |
| --- | --- |
| 限流 | `REQUEST_DELAY=0.2s` |
| 连接复用 | httpx 连接池 |
| 多选择器兜底 | 主要选择器失败时回退备用选择器 |

::: tip 关于数据来源的合规性（已核实）
早期代码注释里写过 "captcha bypass"，但逐行核实后确认：**归类模块实际走的是无验证码的 JSON API + 纯本地检索，并不存在绕过验证码的逻辑**，那句注释是重构后遗留的过时描述，已修正。

真正带验证码的是商务部税率查询模块，它走的是「用户填验证码」的正规人机流程，没有自动绕过。

面试时如果被问到数据合规，可以如实说：系统是聚合式实时查询 + 缓存，依赖上游站点；中长期方向是走官方 API 或数据授权，把核心数据本地化。
:::

## 五、功能清单

网页端与小程序端功能对齐：

| 功能 | 说明 |
| --- | --- |
| 中国 HS 查询 | 搜索 + 详情（退税率、最惠国、增值税、监管条件、申报要素） |
| 英国 / 欧盟 / 美国关税 | 各自独立的搜索与详情页 |
| 批量查询 | 一次查多个编码 |
| 关税对照 | 多国横向对比 |
| 商务部模块 | 各国税费概览、中外编码对照、监管条件、智能归类 |
| 智能归类 | 按商品描述逐层选择章 / 品目 / 子目 |
| **到岸成本计算器** | 算上关税、增值税后的落地成本 |

到岸成本计算器是个亮点——它把"查税率"这个动作往前推了一步，变成"算这笔生意划不划算"，直接服务销售报价场景。

## 六、已知边界

| 边界 | 说明 |
| --- | --- |
| **无内置数据集** | 全部实时抓取 + 缓存，上游挂了就查不了 |
| **无自研搜索** | 模糊匹配能力依赖上游站 |
| **测试覆盖较薄** | 已补 classify 离线测试，其余模块（抓取 / 缓存）待补 |
| **无编码变更历史** | 只展示当前状态（正常/过期/废止），没有建历史版本表 |
| **依赖第三方站** | 上游改版会导致解析失败，需人工跟进 |

::: tip 面试准备：上游挂了怎么办
这是这个项目最容易被问到的问题。标准答法：

1. **短期**：两级缓存兜底——详情页 7 天 TTL，即使上游短暂不可用，高频查询仍有结果
2. **中期**：多数据源互为备份，主源失败切备源
3. **长期**：通过官方 API 或数据授权把核心 HS 数据本地化，把"实时抓取"降级为"定期同步"

这个项目当时的定位是**快速验证需求**，所以选了抓取这条路。如果业务验证成立，下一步必然是数据本地化——承认这一点不会减分，反而说明你知道系统的演进方向。
:::

## 七、交付计划书（路线图）

> 这个系统的定位是「快速验证需求」，所以选了实时抓取。计划书的主线是**把验证过的需求转成可持续的形态**——先去风险，再做厚。

| 阶段 | 目标 | 关键动作 | 状态 |
| --- | --- | --- | --- |
| 近期 | 数据合规去风险 | 走官方 API / 数据授权替换实时抓取，摆脱对上游解析的依赖 | 规划中 |
| 近期 | 补工程底座 | 后端单元 / 集成测试；HS 编码变更历史版本表 | 规划中 |
| 中期 | 数据本地化 | 核心 HS / 税率落 SQLite，抓取降级为「定期同步」，上游挂了不影响查询 | 待启动 |
| 中期 | 自研检索雏形 | 在人工术语表之上加中文分词 / 语义匹配，降低对上游搜索的依赖 | 待启动 |
| 远期 | 多源互为备份 | 主源失败切备源；LLM 辅助智能归类（术语仍人工终审） | 设想 |

::: warning 优先级判断
先走官方 API / 数据授权把数据合规这个根问题解决——实时抓取既脆弱又不可控。然后才是数据本地化，因为本地化是「上游挂了还能查」的根。
:::

## 七、三十秒版本

> 报关员查一个商品的关税和退税率，要在中国 HS、英国 TARIC、欧盟 TARIC、美国 HTS 和商务部五个站点之间来回切。我把这四方数据源聚合成一个后端，网页端和微信小程序共用同一套接口。
>
> 前端用 React 加 Vite，小程序用 Taro 4——选它是因为可以用 React 语法写一套代码同时产出小程序和 H5。
>
> 数据没有本地库，是实时抓取加两级缓存：内存 LRU 做热点，SQLite 做持久化，搜索缓存 24 小时、详情 7 天。术语翻译是人工维护的对照表，不是机翻，因为关税术语翻错会导致归类错误。
>
> 除了基础查询，做了批量查询、多国关税对照、按章品目子目逐级选择的智能归类，还有一个到岸成本计算器——把"查税率"往前推成"算这笔生意划不划算"，直接服务销售报价。
>
> 边界我也说清楚：搜索能力依赖上游站，上游改版就得跟进解析；系统是聚合式实时查询加缓存，没有内置数据集，中长期方向是走官方 API 或数据授权把数据本地化。这个项目当时的定位是快速验证需求，下一步是数据本地化。
