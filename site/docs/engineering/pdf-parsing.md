# PDF 逆向解析：从版式文件到结构化表格

> 亚马逊导出的 Transaction Report 是没有表格标记的版式 PDF。这篇文章讲怎么把它还原成结构化数据，以及踩过的坑。

## 一、问题的本质

普通的 PDF 解析（pdfplumber、PyMuPDF 的 `get_text()`）能工作，前提是 PDF 里有**文本层**——字符带着坐标信息。这个前提亚马逊的报表是满足的。

真正的问题是：**有文本层 ≠ 有表格结构。**

PDF 内部没有"行"和"列"的概念，只有一串带着 `(x, y)` 坐标的文本片段。你拿到的是这样一堆东西：

```text
(72.0, 100.5) "Product Sales"
(72.0, 112.3) "Shipping Credits"
(72.0, 124.1) "FBA Fees"
(480.0, 100.5) "1,234.56"
(480.0, 112.3) "89.20"
(480.0, 124.1) "-156.78"
```

表格的"左栏是科目名、右栏是金额"这个结构，是**人看出来的**，PDF 里并没有声明。

## 二、解决思路：坐标聚类重建

```text
1. 提取所有文本 span（带 x, y 坐标）
2. 按 x 坐标聚类 → 识别出「栏」
3. 按 y 坐标聚类 → 识别出「行」
4. 行内按 x 排序 → 拼成 (科目名, 金额) 对
```

实现上用 PyMuPDF 的 `get_text("dict")`，它直接返回带 bbox 的结构化 span，比解析纯文本再猜坐标可靠。

**跨页天然支持**：循环逐页提取后合并 span 列表，不需要特殊处理页面边界。

## 三、真正的难点：行漂移

理想情况下同一行的 y 坐标完全相同。现实是：

```text
科目名在 y=100.5，金额在 y=100.5    ← 理想
科目名在 y=100.5，金额在 y=103.2    ← 常有
科目名在 y=100.5，金额在 y=112.0    ← 日文 PDF
```

如果只是按 y 排序再配对，稍微有点漂移就会**把 A 科目的金额配给 B 科目**。这在做账工具里是致命错误。

### 解法：7px 高度窗口

行分组不用精确相等，而是用**固定 7px 的高度窗口**：y 坐标落在同一窗口内的 span 视为同一行。

这个数值是实测调出来的——足够宽容以吸收常规漂移，又足够严格以避免相邻行粘连。

### 特例：日文 PDF 的 11px 下漂

日文 PDF 的金额整体下漂 **11–12px**，直接落到下一行的窗口里，产生"孤儿金额"——某个金额找不到归属的科目行。

解法是**孤儿金额再分配**：

```text
检测：某个 y 窗口里只有金额、没有科目名
处理：向上查找最近的同名科目行，把金额归并进去
```

::: tip 这个设计的价值在哪
价值不在算法多高深，而在**分层**：

| 层 | 处理 | 特点 |
| --- | --- | --- |
| 通用层 | 7px 窗口行分组 | 覆盖绝大多数语言 |
| 特例层 | 孤儿金额再分配 | 只针对日文版式 |

**没有用一个 hack 覆盖掉通用逻辑。** 常见的错误做法是"窗口调大到 15px 顺便解决日文"，那样会让其他语言的行粘连。

保持通用规则干净，特例单独加补丁并注明原因——这样后续维护的人知道哪条规则为什么存在。
:::

## 四、多语言识别

### 语言检测

对 11 种 locale 做**关键词打分**：

| 命中类型 | 分值 |
| --- | --- |
| section 关键词 | +2 |
| skip 文本 | +1 |
| 科目名 | +3 |

取总分最高的 locale。

**为什么用打分而不是更"聪明"的方法**：关键词打分的结果是可解释、可调试的。检测错了，打印分数表就知道是哪个词没命中。用分类器虽然可能更准，但错了没法排查。

### 科目名映射：两级

```text
1. 字典精确匹配
2. difflib.SequenceMatcher 模糊匹配，阈值 0.80
```

模糊匹配阈值的选择是权衡：

- 太高（0.95）→ 很多正常变体匹配不上，全落到人工复核
- 太低（0.60）→ 不同科目被误配，产生错误数据

0.80 是实测的平衡点。GUI 里对 0.80–0.85 区间标黄、低于 0.80 标红，**把不确定性的程度可视化给人工复核**。

## 五、数字格式归一

五种正则覆盖不同语种习惯：

| 格式 | 正则覆盖 | 样例 | 语种 |
| --- | --- | --- | --- |
| 英式 | 逗号千分位、点小数 | `1,234.56` | en |
| 欧式 | 点千分位、逗号小数 | `1.234,56` | de / fr / es / it |
| 无分隔符 | — | `1234.56` | 部分站点 |
| 整数制 | 无小数 | `27130` | ja（JPY） |
| 零值 | — | `0.00` | 通用 |

### 一个隐蔽的坑：Unicode 减号

PDF 里的负号经常是 **U+2212（−，MINUS SIGN）** 而不是 ASCII 的 `-`。它长得像，但 `float("−123")` 会直接抛异常。

必须在解析前做归一化：

```python
text.replace("\u2212", "-")   # Unicode 减号 → ASCII
```

这类问题的特点是**只在特定语言、特定版本的 PDF 上出现**，本地测试用英文样本根本发现不了。

## 六、货币推断

优先级：

```text
1. 正则提取声明文本，如 "All amounts in EUR"
2. 失败 → 回退 locale → 币种映射表
3. 海湾国家特例：用 KSA、GMT+4、GMT+3 这类线索推断 SAR / AED
```

海湾国家那一步是因为阿联酋和沙特的 PDF 用的 locale 标识不规范，只能靠时区和地名线索。

## 七、V16 / V17 符号模式

`value_mapper.py` 里的模块级开关 `_SIGN_TRANSFORM`：

| 版本 | 支出行 | 转账/税行 |
| --- | --- | --- |
| V16 | 保持原值 | 保持原值 |
| V17 | **取反** | 取绝对值 |

**这不是版本新旧关系**，而是按客户会计模板打包的变体——不同客户对费用、税款的正负号约定不一样。

设计上：

- SaaS 版在请求级别切换（`_vm._SIGN_TRANSFORM = sign_transform`）
- 桌面版改常量

::: warning 一个设计缺陷
桌面版 GUI **没有暴露这个开关**，只能改代码。

如果客户需要切换模式，就得重新打包。更好的做法是做成配置文件或 GUI 选项。这是个真实的改进点。
:::

## 八、校验：不要相信解析结果

解析完不能直接用。`validator.py` 有 5 条规则：

| 规则 | 内容 |
| --- | --- |
| R1 | 分节小计一致 |
| R2 | 总额 sanity（收入 ≥ 0，费用 ≤ 0） |
| R3 | 完整性检查 |
| R4 | 未映射科目提醒 |
| R5 | 关键科目必须存在 |

::: warning 这里有个容易误解的点
这 5 条规则**不做严格借贷平衡校验**。README 里"借贷总额平衡"的说法，指的是亿企代账链路里的 `validate_balance`（容差 0.01，要求每个凭证号下本币与外币借贷合计相等），**不是解析阶段的能力**。

面试时要分清楚这两个阶段。
:::

## 九、方法论总结

把这个项目的做法抽象成可复用的思路：

| 原则 | 做法 |
| --- | --- |
| **分层处理通用与特例** | 7px 窗口是通用规则，孤儿再分配是日文特例，不混在一起 |
| **可解释优先于"聪明"** | 关键词打分而非分类器，错了能排查 |
| **把不确定性可视化** | GUI 颜色分级，让人工复核知道该看哪里 |
| **不信任解析结果** | 5 条校验规则 + 人工复核闸门 |
| **够用就停** | 早期试过 OCR（easyocr + torch），确认文本层够用后把依赖从打包里排除 |

::: tip 最后一原则值得强调
引入 OCR 意味着引入 torch，exe 体积翻几倍、启动变慢、打包复杂度上升。而实际样本证明 PyMuPDF 文本层已经够用。

**砍掉它比加上它更难，但更正确。**
:::

## 十、如果重做，我会改什么

| 改进点 | 说明 |
| --- | --- |
| 括号负数 | 当前正则未覆盖 `(1,234.56)` 表示负数的情况 |
| V16/V17 开关配置化 | 桌面版不用改代码重打包 |
| 借贷平衡前移 | 解析阶段就应该有平衡校验，不等到凭证层 |
| 版式规则外置 | 把 7px 窗口、孤儿阈值等做成配置，加新语种不用改代码 |
| 回归样本库 | 把各国 PDF 样本固化成回归测试集，改动时自动验证 |
