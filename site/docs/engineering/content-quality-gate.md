# 内容质量门禁：让 AI 生成的内容能自动判生死

> AI 生成内容最大的问题不是"写得不好"，而是"你不知道它写得好不好"。这篇讲怎么把主观的质量判断，变成可自动执行的硬约束。

## 一、问题定义

用 LLM 批量生成内容，你会立刻遇到三个问题：

| 问题 | 后果 |
| --- | --- |
| 质量不稳定 | 同一套 prompt，这次能用下次是垃圾 |
| 事实不可控 | 模型会编造数字、承诺、案例 |
| 无法规模化 | 靠人工逐篇审稿，生成得再快也没用 |

**核心矛盾：生成速度是指数级的，人工审核是线性的。**

解法只有一个——**把审核标准代码化**。

## 二、整体架构

GEO 系统的质量把控分四道：

```text
生成阶段        生成后            发布前              发布后
   │              │                 │                  │
honest_judge  content_       platform_variant_    效果追踪
模型自审      quality_gate     guard              （收录率、
（最多2轮）   结构性准入       平台特化校验        探针命中）
   │              │                 │                  │
   └── 第一道 ────┴── 第二道 ───────┴── 第三道 ────────┘
```

| 关卡 | 模块 | 职责 |
| --- | --- | --- |
| 第一道 | `honest_judge` 循环 | 让模型自审，不通过则修复重跑 |
| 第二道 | `content_quality_gate.py` | 12 项结构性硬检查 |
| 第三道 | `competitor_claim_guard.py` | 无来源数字断言处理 |
| 第四道 | `platform_variant_guard.py` | 按平台差异化校验 |

## 三、第一道：让模型扮演检索系统

### 设计

`HONEST_JUDGE_SYSTEM` 的 prompt 开头：

> 你是 DeepSeek AI 搜索引擎的检索系统……

然后让模型判断「我会不会引用这篇文章」，覆盖 8 个维度：RAG 切片友好度、实体密度、反偏见、来源真实性等。

`judge_passed()` 解析回复第一句的"会/不会"，不通过就 `fix_article()` 按 critique 逐条修复后回炉。

### 为什么是"扮演检索系统"而不是"评价质量"

这是个关键的设计选择：

| 问法 | 性质 | 问题 |
| --- | --- | --- |
| "这篇文章质量怎么样？" | 主观题 | 模型倾向给好评，输出模糊 |
| "你会不会引用这篇？" | **接近客观题** | 有明确的判断依据，输出可解析 |

评价"好不好"是审美判断，评价"引不引"是**行为模拟**——后者更接近你要优化的真实目标。

### 成本刹车

```text
max_rounds = 2    # 最多两轮 judge-fix 循环
```

不允许无限迭代。两轮还不过关就判定这篇选题不行，换候选重来。

::: tip 为什么不设成 3 轮或更多
收益递减 + 成本线性增长。实测两轮已经能过滤掉大部分问题；第三轮的边际改善很小，但 token 成本照付。

**这是一个明确的工程权衡，不是默认值。**
:::

## 四、第二道：结构性硬检查

`content_quality_gate.py` 的阈值写在模块顶部，全部是硬编码常量：

```python
SIMILARITY_LIMIT                 = 0.55   # 与已有内容相似度上限
VARIANT_SOURCE_SIMILARITY_LIMIT  = 0.75   # 变体 vs canonical
VARIANT_SIBLING_SIMILARITY_LIMIT = 0.72   # 变体 vs 其他平台变体
```

### 12 项准入清单

| 检查项 | 要求 | 为什么 |
| --- | --- | --- |
| 相似度 | ≤ 0.55 | 防止同质内容 |
| `original_evidence` | 必须有 | 必须有原创证据，不能是拼凑 |
| H1 | 存在 | 结构完整 |
| H2 | ≥ 2 个 | 有分节，便于切片 |
| FAQ | ≥ 3 条 | **AI 搜索爱抓问答对** |
| 对比表 | 必须有 | 结构化信息密度高 |
| `source_block` | 必须有 | 来源可验证 |
| `update_block` | 必须有 | 时效声明 |
| 作者 | 必须有 | 责任主体 |
| canonical | 必须有 | 防重复内容 |
| `unsupported_commercial_claim` | 为零 | 见下一节 |
| `brand_overuse` | **≤ 12 次** | 见下文 |
| `promotional_headline` | 不得促销化 | 标题不能像广告 |

### 最反直觉的一条：品牌词超过 12 次就拦截

做内容的人本能地想多提品牌。但这条规则反过来限制你。

原因是一个被很多人忽略的事实：**过度自我推销的内容会被 AI 判定为广告而拒绝引用。**

AI 搜索要给用户"客观答案"，不是"广告文案"。品牌词密度是判断内容性质的强信号。

## 五、第三道：数字中性化

`competitor_claim_guard.py` 处理无来源的数字断言：

```text
"3 天送达"        →  有来源？没有 → 降级
"成本降低 40%"    →  有来源？没有 → 降级
```

### 关键：是降级不是删除

`_QUALIFICATIONS` 提供 5 种合规话术，把具体数字替换成定性表述：

| 原表述 | 降级后 |
| --- | --- |
| "3 天送达" | "具体时效以实际合同为准" |
| "成本降低 40%" | "实际成本因方案而异" |

::: tip 为什么删除不是好办法
直接删掉数字断言，文章会变得空洞、没有信息量，反而不被 AI 引用。

降级成定性表述，保留了话题完整性，同时规避了两重风险：

1. **合规风险**：虚假宣传
2. **可信度风险**：AI 会判定无来源的数字不可信

**这不是 censorship，是 risk rephrasing。**
:::

## 六、第四道：平台差异化

`platform_variant_guard.py` 对不同平台用不同严格度：

| 平台 | 来源阈值 | 历史阈值 | 原因 |
| --- | --- | --- | --- |
| 百家号 | **0.32** | **0.42** | 原创校验最狠，封号成本最高 |
| 其他 | 0.55 | 0.50 | — |

还有**内容形态的针对性改造**：

`prepare_sohu_editorial_variant()` 把搜狐版本改造成"中性行业观察"，**主动删除品牌实体、数字、表格、链接**。

这是对平台审核规则的适配——搜狐对商业推广内容的审核更严，中性行业观察的过审率高得多。

## 七、设计原则总结

| 原则 | 体现 |
| --- | --- |
| **硬阈值优于模型判断** | 相似度、FAQ 数量这些能算的就算，不交给 LLM |
| **模型只做算不了的事** | 语义质量、是否值得引用，这些才用 LLM |
| **不信任单次输出** | judge → fix → judge 最多两轮 |
| **失败要有明确原因** | 每个检查项都是独立判定，失败时知道卡在哪 |
| **成本要可控** | `max_rounds`、有界候选池 |

::: tip 最重要的一条：能算的别交给模型
用 LLM 判断"这篇文章好不好"很容易，但那是把确定性换成概率。

**结构性检查（有几个 H2、有几条 FAQ、相似度多少）应该用代码算**——结果确定、成本为零、可调试。

只有真正需要语义理解的判断，才值得付 token。
:::

## 八、真实效果与已知问题

### 效果

| 指标 | 数值 |
| --- | --- |
| 候选被门禁拒绝后换下一个 | 常态 |
| 候选池耗尽 | 留 `failed_no_candidates` 可操作记录 |
| 兜底改写 | `build_evidence_first_fallback()` → `build_topic_quality_fallback()` |

### 已知问题

| 问题 | 说明 |
| --- | --- |
| 相似度依赖 difflib | 词面相似，对改写后语义相同的内容不敏感 |
| 阈值是拍出来的 | 0.55 / 0.75 / 0.72 来自实测调参，没有系统性标定 |
| 兜底内容质量偏低 | 两次兜底后的内容明显弱于首选候选 |
| 无人工抽检闭环 | 通过了门禁的内容没有人工复核样本 |

::: tip 如果要改进
最有价值的一步是**建立人工抽检闭环**：定期抽 20 篇通过了门禁的内容人工打分，用打分结果回标阈值。

现在的阈值是"感觉差不多"，有数据之后才能变成"最优值"。
:::

## 九、这套思路能迁移到哪

不局限于内容生成。任何"AI 批量产出 → 需要自动验收"的场景都适用：

| 场景 | 硬检查 | 模型判断 |
| --- | --- | --- |
| AI 生成代码 | lint、测试覆盖率、复杂度 | 可读性、是否符合架构 |
| AI 生成测试用例 | 覆盖率、断言数量 | 测试是否有意义 |
| AI 生成客服回复 | 敏感词、品牌词、承诺词 | 语气是否合适 |
| AI 生成数据分析 | 数字与源数据一致 | 结论是否合理 |

**共同模式：结构性问题用代码算，语义问题用模型判，两道都要有。**
