# 知识工程与 RAG：什么时候该放弃向量检索

> 我实现过 RAG，然后在新版本里把它砍了。这篇讲这个决策背后的判断，以及知识组织比检索算法更重要。

## 一、先说结论

在 [AI 智能客服](/projects/ai-cs) 项目里：

| 版本 | 方案 |
| --- | --- |
| 旧版（main 分支） | **标准 RAG**：embedding + 余弦相似度检索 |
| 新版（工作树） | **直接知识上下文**：放弃向量库，精炼 Markdown 全量拼进上下文 |

这不是"新版没做完所以没接检索"，而是**刻意的取舍**。

## 二、两套方案对比

### 方案 A：标准 RAG

```text
文档 → chunking → embedding → 向量库
                                 ↓
用户提问 → embedding → 相似度检索 → top-k 片段 → 拼进 prompt → 生成
```

实现细节：`ragService.js` 的 `getEmbedding` + 余弦相似度，向量库存内存 JSON。

### 方案 B：直接上下文

```text
精炼 Markdown（status=approved 且 visibility=customer）
        ↓
   按业务线作用域筛选
        ↓
   全量拼进系统提示
        ↓
   生成
```

由环境变量 `GROUP_AI_ENABLED` 切换，未开启则回退旧 RAG。

## 三、为什么砍掉 RAG

### 判断依据：知识库的特征

| 特征 | RAG 适合 | 直接上下文适合 |
| --- | --- | --- |
| 知识规模 | 海量文档（万篇以上） | **精炼后有限（几十 KB 级）** |
| 知识来源 | 原始文档、历史记录 | **人工编写维护** |
| 准确性要求 | 允许一定噪声 | **要求确定、可预期** |
| 更新频率 | 高频自动同步 | 低频人工更新 |

客服知识库的实际特征是：**人工精炼过的、总量有限的、要求准确的**。

服务范围、价格区间、流程说明、常见问题——这些本来就是人写好的，不是从海量文档里挖的。

### RAG 在这个场景下的真实问题

| 问题 | 说明 |
| --- | --- |
| **检索会偏** | 用户问法稍变，检索到的片段就变了，答案也变 |
| **错误静默** | 检索到错误的片段，模型照样基于它生成，看不出问题 |
| **调参黑洞** | chunk 大小、切分策略、top-k、相似度阈值，每个都要调 |
| **排查困难** | 答错了，是知识没写？切分不对？检索偏了？还是模型问题？ |

**最后一条最致命。** 客服答错是要付业务代价的，而 RAG 让"为什么答错"变成一个四选一的问题。

### 直接上下文的优势

| 优势 | 说明 |
| --- | --- |
| **行为确定** | 知识就那些，全给了，不存在"没检索到" |
| **排查简单** | 答错了只有两种可能：知识写错了，或者模型理解错了 |
| **维护直观** | 改 Markdown 就生效，不用重新切分、重新算向量 |
| **零检索延迟** | 省掉 embedding 调用 |

::: tip 面试怎么讲这个决策
关键不在于"哪个技术更先进"，而在于**你能说清楚为什么这个场景不需要它**：

> 我先做了 RAG，能用。但我判断客服知识库是人工精炼的、总量有限的、要求准确可预期的，这种情况下把全部知识直接给模型，比让向量检索去猜"哪段相关"更可控。检索偏了会静默出错，而全量上下文的行为是确定的，排查也容易。

**"我知道怎么用，但我判断这里不需要"——比"我用了"更有说服力。**
:::

## 四、真正重要的是知识工程，不是检索算法

砍掉 RAG 之后，重心反而更清楚了：**知识本身的质量和组织方式才是决定性的。**

### 知识分层

| 层 | 内容 | 作用域 |
| --- | --- | --- |
| 集团公共信息 | 公司概况、联系方式 | 全业务线 |
| 美鸥元财税合规 | 服务范围、流程、资质 | `businessHint="meiouyuan"` |
| SharkBox 海外仓 | 仓储服务、时效、报价区间 | `businessHint="sharkbox"` |

每条知识有两个关键字段：

```text
status: approved          # 只有审核通过的知识才进上下文
visibility: customer      # 只有对客可见的知识才用
```

::: tip 这两个字段是系统的核心
它们把"哪些知识能用"从代码逻辑变成了**数据状态**。

运营人员改一条知识的 `status`，立刻生效，不用改代码、不用重新训练、不用重新切分。

**知识治理靠数据模型，不靠代码分支。**
:::

### 业务路由

`business/router.js` + `classifier.js` 做 LLM 分类，决定用哪个作用域的知识。

关键优化：**页面级 `businessHint` 可复用**。

```tsx
<GroupAiWidget businessHint="meiouyuan" />
```

用户从财税合规页面点开客服，系统已经知道他在问财税，不用再问一遍"您咨询哪方面"。

这是 [合规官网](/projects/compliance-site) 和客服系统的一体化证据。

## 五、防止模型胡说：输出侧护栏

知识组织得再好，模型仍可能越界。所以必须有**输出侧校验**。

### 输入侧 `detectInputRisk`

防提示词注入、防敏感信息泄露。

### 输出侧 `outputPolicyViolation`

对财税合规业务线，拦截：

| 拦截内容 | 风险 |
| --- | --- |
| 具体报价数字 | 商务承诺 |
| 保证退税结果 | **法律承诺** |
| 保证合规结果 | **法律承诺** |
| 个案税务结论 | **专业责任** |

::: tip 为什么必须在代码层做，不能只靠 prompt
在 prompt 里写"不要承诺退税结果"，是**建议**。
在输出侧做正则拦截，是**约束**。

财税合规是强监管领域。AI 随口说一句"这个能退税"，就是实打实的法律风险，而且是**以公司名义对客户做出的承诺**。

**把合规要求从提示词升级成系统约束，是这个项目最重要的一次设计决策。**
:::

### 可追溯 `traceService`

每条回答留痕来源轨迹——基于哪些知识片段生成的。出问题能倒查：是知识写错了，还是模型理解偏了。

## 六、人工转接：知道 AI 不该答什么

| 触发条件 |
| --- |
| 用户明确要求人工 |
| 询问具体价格 / 合同 |
| 涉及个案的税务或法律结论 |
| 投诉、货损、赔偿 |

::: tip 这个清单本身就是知识工程的产物
它不是拍脑袋定的，而是对着**业务风险**逐条梳理出来的：

- 报价和合同 → 商务决策，AI 不该替公司定价
- 个案税务法律结论 → 专业责任，AI 不能担
- 投诉赔偿 → 情绪 + 责任，AI 处理不了

**一个 AI 客服的成熟度，不取决于它能答多少问题，而取决于它知道多少问题不该答。**
:::

## 七、方法论：RAG 该不该用的判断树

```text
知识总量 > 模型上下文承受上限？
├─ 是 → 需要检索（RAG / 混合检索 / 分层检索）
└─ 否 → 知识是否是人工精炼的？
        ├─ 是 → 直接全量上下文（行为确定、好排查）
        └─ 否（原始文档堆）→ 需要先做知识工程：
                              清洗 → 分层 → 审核 → 精炼
                              精炼后再判断是否还需要检索
```

::: tip 最重要的一句
**大部分"RAG 效果不好"的问题，其实不是检索算法的问题，是知识没整理好。**

先花时间把知识清洗、分层、审核、精炼，很多场景下就不需要 RAG 了。即使需要，效果也会好得多。
:::

## 八、已知边界

| 边界 | 说明 |
| --- | --- |
| 旧版向量库在内存 | 进程重启需重建，未持久化 |
| 无知识版本管理 | 改了知识没有历史记录，出问题难回溯 |
| 无人工抽检闭环 | 没有定期抽检回答质量并回标的机制 |
| 未上线 | 原型完成，集团版开发中未合并 |
| 阈值靠拍 | 人工转接触发规则来自业务梳理，无数据验证 |
