# 发布可靠性工程：外部平台不可控时怎么办

> 发布到别人的平台，你控制不了它的 API、审核规则、可用性和返回格式。这篇讲在这种环境下怎么保证不重发、不漏发、失败可追。

## 一、问题定义

把内容发布到百家号、头条、搜狐、知乎、掘金这些平台，你面对的是：

| 不可控因素 | 表现 |
| --- | --- |
| **无发布 API** | 只能用 Playwright 做 UI 自动化 |
| **审核规则不透明** | 同样的内容有时过有时不过 |
| **页面结构会变** | 选择器失效是常态 |
| **无幂等保证** | 重跑可能发布两遍 |
| **无可靠回调** | 发没发成，得自己去查 |

**核心矛盾：你的系统是确定性的，外部平台不是。**

## 二、四个必备能力

| 能力 | 作用 |
| --- | --- |
| **幂等** | 同样的内容不会发两遍 |
| **状态分离** | 区分"提交成功"和"真的可见" |
| **有界重试** | 失败了重试，但不能无限循环 |
| **可操作失败记录** | 最终失败时，留下的记录能指导人工介入 |

## 三、幂等：发布前先查

`matrix_local_publisher.py` 用 `logs/matrix_state.json` 作为状态机，发布前调 `already_published()` 检查。

### 真实数据

日志里有 **14 条 `reason: already_published` 的跳过记录**。

::: tip 这个数字为什么重要
幂等机制**在生产中真的生效过 14 次**，不是"写了但没触发过"的摆设。

这说明重跑是常态——调度器重启、脚本中断、人工重跑，都会触发幂等检查。**没有这层，就是 14 次重复发布。**
:::

### 幂等键的设计

用 `content_id` + `platform` 作为键，而不是内容哈希。

原因：同一篇内容在不同平台是不同记录，但同一篇内容**在同平台发第二次就是重复**。用内容哈希的话，改了一个标点就会绕过幂等检查。

## 四、状态分离：发布 ≠ 可见

这是这套系统里最少见、也最有价值的设计。

### 四个状态

| 状态 | 含义 |
| --- | --- |
| `public_visible` | 回访公开 URL，确认真的能访问 |
| `draft_saved` | 存进草稿了，但没发布出去 |
| `unverified` | 提交成功但没验证过 |
| `failed` | 失败 |

### 真实分布

| 状态 | 数量 |
| --- | --- |
| `public_visible` | 22 |
| `draft_saved` | 8 |
| `unverified` | 6 |
| `failed` | 3 |

::: tip 为什么"存草稿"必须单独区分
现在很多平台有"发布后进入审核"和"直接存草稿"两条路径。UI 自动化的返回值可能都是"操作成功"，但实际结果天差地别。

如果不做回访验证，你会以为 30 篇都发出去了，实际有 8 篇躺在草稿箱。

**"提交成功"是你说的话，"公开可见"是平台的状态。这两件事必须分开记录。**
:::

### 实现

`verify_after_publish()` 回访公开 URL，把验证结果写回 state。

## 五、有界重试：有限候选池

这是整个设计里最硬的一条规则，来自 `AGENTS.md`：

> 当日候选稿被质量门禁拒绝时，外层调度器**必须**请求新候选，逐一评估，**不得**在第一次失败后结束当日运行。
> 使用**有界重试池**，防止坏候选无限循环。
> 池子耗尽时，留下一份**包含每条拒绝原因**的可操作失败记录。

### 为什么是"换候选"而不是"重试同一篇"

内容被质量门禁拒绝，通常是因为**选题或角度不行**，不是随机波动。重试同一篇大概率还是不过。

所以正确做法是**换一个候选重新走完整流程**，而不是重试被拒的那一篇。

### 有界的实现

```text
候选池（有界）
   ↓ 取一个
生成 → 质量门禁
   ↓ 通过 → 发布
   ↓ 拒绝 → 记录原因 → 取下一个
   ↓ 池空 → failed_no_candidates + 完整拒绝原因
```

`external_platform_candidate_pool.py` 把状态落盘到 `logs/external_platform_candidate_pool_state.json`，状态枚举含 `failed_no_candidates`。

`simulate_geo_candidate_pool.py` 在候选池耗尽时**返回非 0 退出码**，让调度器能感知失败。

::: tip "可操作"三个字是关键
失败记录不能只写"今天发布失败"，必须写清楚：

| 字段 | 用途 |
| --- | --- |
| 每个候选被拒的**具体原因** | 知道是选题问题还是生成质量问题 |
| 拒绝时的相似度/阈值 | 知道差多少 |
| 池子规模 | 知道是候选不够还是质量不行 |

有了这些，人工介入时不用重新跑一遍就知道问题在哪。
:::

## 六、限流与节流

`publish_schedule.json` 的参数：

| 参数 | 值 | 目的 |
| --- | --- | --- |
| `daily_publish_limit` | 3 | 每日总量 |
| `platform_limits` | 2 | 单平台上限 |
| `min_interval_minutes` | 120 | **最小间隔** |
| `publish_hours` | 9–21 | 时段窗口 |
| `content_b2b_ratio` | 0.6 | B2B/B2C 配比 |

`matrix_strategy.json`：

| 参数 | 值 |
| --- | --- |
| `owned_site_limit` | 1 |
| `external_variant_limit` | 3 |
| `platform_order` | news → baijiahao → toutiao → sohu → csdn → zhihu |

::: tip 最小间隔 120 分钟是防封号设计
短时间内从同一 IP 向同一平台密集发布，是**最典型的被判定为机器行为、导致封号**的模式。

这些参数不是性能优化，是**风控**。
:::

## 七、发布成功率数据

2026-07-15 → 2026-09-02（约 50 天）：

| 平台 | 执行 | 成功 | 失败 | 成功率 |
| --- | --- | --- | --- | --- |
| 头条 | 34 | 29 | 5 | 85% |
| 百家号 | 34 | 27 | 7 | 79% |
| 搜狐 | 29 | 20 | 9 | **69%** |
| 知乎 | 21 | 19 | 2 | 90% |
| 掘金 | 3 | 2 | 1 | 67% |
| **合计** | **121** | **97** | **24** | **80%** |

::: tip 怎么解读这个数据
**80% 成功率看起来不高，但这恰恰是真实系统的样子。**

如果一个系统的对外发布成功率是 100%，通常意味着：
- 它跑的次数太少，还没遇到失败
- 或者它把失败静默吞掉了

**能测出"搜狐只有 69%"这个结论，说明系统真的跑得够久、记录得够全。**

而且这个数据驱动了后续决策：搜狐审核最严，所以给它做了专门的"中性行业观察"变体改造（删品牌、删数字、删表格、删链接）。
:::

## 八、一个反面案例：RPA 缺了什么

对比一下 [RPA 工具链](/projects/rpa) 在可靠性上的缺失，能更清楚地看出这套设计的价值：

| 能力 | GEO 发布系统 | RPA 工具 A |
| --- | --- | --- |
| 幂等 | ✅ 14 次真实生效 | ❌ 无前置检查，重跑会重复打标 |
| 状态分离 | ✅ 四状态 | ❌ 无状态记录 |
| 有界重试 | ✅ 候选池 + 非 0 退出码 | ❌ 无重试 |
| 失败记录 | ✅ 含拒绝原因 | ⚠️ 仅 `console.error` |
| 限流 | ✅ 三层限流 | ❌ 无 |
| 持久化审计 | ✅ JSON 状态文件 | ❌ 内存，重启即丢 |

**同样是"用 Playwright 操作别人的系统"，可靠性设计的差距决定了能不能长期无人值守运行。**

## 九、可复用的设计清单

任何"向不可靠外部系统写入"的场景都适用：

| 项 | 检查 |
| --- | --- |
| ✅ 幂等键 | 用什么保证同一操作不重复执行？ |
| ✅ 状态机 | 有哪些状态？"提交"和"生效"分开了吗？ |
| ✅ 回访验证 | 怎么确认真的生效了，而不是只收到了 200？ |
| ✅ 有界重试 | 重试上限是多少？超限后怎么办？ |
| ✅ 失败记录 | 记录里有没有下一步动作需要的信息？ |
| ✅ 限流 | 有没有频率控制避免触发对方风控？ |
| ✅ 持久化 | 进程重启后状态还在吗？ |

::: tip 一句总结
**外部系统不可靠是前提，不是意外。所有设计都要在这个前提下成立。**
:::
