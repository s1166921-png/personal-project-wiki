# 自动化安全边界：脚本要动真实数据，怎么兜底

> 自动化最大的风险不是脚本写错，而是**脚本按预期执行了，但预期本身是错的**。这篇讲几个项目里真实落地的安全设计。

## 一、核心原则

| 原则 | 说明 |
| --- | --- |
| **默认不写** | 危险操作的默认配置必须是 dry-run |
| **只读优先** | 能只读就别写，写操作交给人工 |
| **存在性不泄露** | 无权限返回 404，不是 403 |
| **不信任输入** | 文件名、路径、ID 都服务端生成或校验 |
| **失败要留证** | 出问题时能还原现场 |

## 二、第一道防线：默认 dry-run

### RPA 运单标识

这个脚本要在真实仓储系统里**勾选标识**，是实打实的写操作。

```json
// config.json —— 默认值就是不写
"behavior": { "dryRun": true }
```

`executeMark(page, dryRun)` 在 dry-run 模式下：

```text
1. 正常打开标识弹窗      ← 走完整流程，暴露所有问题
2. 跳过"执行"按钮点击    ← 唯一的区别
3. 按 Escape 关闭弹窗
```

::: tip 为什么 dry-run 要走完整流程，而不是直接跳过
这是这个设计的关键。

很多 dry-run 实现是"碰到写操作就 return"，那样**只有写操作没被验证**。

真实的 dry-run 应该走完所有步骤——登录、搜索、打开弹窗、填参数、截图——**只在最后一次点击前停住**。

这样能验证：选择器还对不对、数据取对了没、会操作到哪些记录。

**暴露问题才是 dry-run 的价值，不是跳过问题。**
:::

流程上也强制：先 `npm run rpa:dry` 演练、人工确认截图无误，再 `run-real.ps1`。

这套设计的核心是**让默认行为站在安全侧**：演练不写实盘、确认后才执行。任何想跳过确认的脚本改动都会让 dry-run 失灵——而 dry-run 失灵是一次测试就能发现的问题，不会偷偷跑到生产。

## 三、第二道防线：只读优先

### 物流对账机器人

对账要在 TMS 系统里逐单搜索、比对金额和费用类型。

**设计决策：对 TMS 只做读操作。**

```text
fill（填运单号）→ click 搜索 → 读取表格 → 本地比对
                                      ↓
                              生成差异 Excel（本地）
```

::: tip 为什么不让脚本自动修正
对账是**发现问题**的动作，不是**修正数据**的动作。

- 金额不符可能是 TMS 录错了，也可能是物流商账单错了，还可能是汇率口径不同
- 脚本判断不了这三种情况
- 自动改账是灾难

**正确姿态：只读 + 输出差异报告 + 交人工复核。**
:::

输出四分类，每一类对应不同的人工处理方式：

| 标记 | 含义 | 人工动作 |
| --- | --- | --- |
| ✅ | 一致 | 无需处理 |
| 📋 | 金额不符 | 核对原始单据 |
| 📋 | 费用类型不匹配 | 确认归类口径 |
| 📋 | TMS 无此运单 | 查是否漏录 |

## 四、第三道防线：不信任任何外部输入

### 文件命名：UUID 由服务端生成

SOP 视频上传：

```python
# file_service.py
filename = uuid.uuid4().hex + ext   # 服务端生成
```

用户上传的原始文件名**只作为元数据保存，绝不参与路径拼接**。

::: danger 对照：常见的错误写法
```python
# 危险：用户可控文件名直接拼接
path = os.path.join(upload_dir, file.filename)
# 用户传 "../../etc/passwd" 就穿出去了
```

**规则：任何进入文件系统路径的字符串，必须由服务端生成或经过白名单校验。**
:::

配合类型白名单（mp4 / webm / quicktime / x-msvideo）和大小限制（500MB）。

### 客户隔离：404 而不是 403

`_check_customer_owner` 保证客户只能看自己的视频。访问他人资源时：

```text
返回 404（不存在）   ← 正确
返回 403（无权限）   ← 错误：泄露了"这个资源存在"
```

::: tip 这是信息泄露的经典陷阱
403 告诉攻击者"你猜对了，这个 ID 确实有东西"。枚举 ID 就能画出整个系统的数据地图。

**无权限和无资源，对外部应该表现一致。**
:::

配合模型层隔离：`VideoPublicInfo` **不含 price 字段**，工人端拿不到报价。这一条有专门的端到端断言。

### 凭证管理

| 措施 | 说明 |
| --- | --- |
| 环境变量 | `WAREHOUSE_USERNAME` / `WAREHOUSE_PASSWORD`，不写死 |
| 非 root 运行 | Docker 容器用 `appuser` |
| JWT + bcrypt | 密码不明文存储 |
| `?token=` 兼容 | 因为 `<video>` 标签无法自定义请求头 |

## 五、第四道防线：业务层的防呆

### 凭证防重复入账（做账工具）

财务数据最怕的是**同一笔账入两次**。

```text
每个源文件算 SHA-256
    ↓
同一路径或相同哈希出现两次 → 抛 ImportPreparationError
    ↓
任务号 = sha256(公司名 + 期间 + 排序后的源文件哈希)[:16]
```

任务号的设计也有讲究：**不含账号、密码、验证码**，可以安全地写进日志和产物。

另外全零批次走 `skipped_no_data` 分支，**不创建任何产物**——空文件比没有文件更危险，可能被误当成"已处理"。

### 定价工作流（SOP 视频）

```text
pending →（审核员定价）→ pending_confirmation →（客户确认）→ approved
```

**硬性规则：pending 不能直接 approve，必须先走定价流。**

这是**业务约束代码化**的例子：报价—确认是商务环节，容易被绕过（比如审核员直接通过），把它做成状态机的强制路径，就绕不过去了。

### 凭证号连续性与空类别不占号（做账工具）

```text
每个国家内：Income → Expenses → Transfers → Tax
仅当 |amount| > 0.005 才生成凭证并占号
```

空类别不占号——否则会出现"001、002、004"这种断号，财务对不上账。

反序输入国家也要保证输出一致，有专门测试覆盖。

## 六、一个值得记住的案例：文档与代码的一致性

做账工具的 README 写着"支持 8 种语言"，并且列了一个代码里**不存在**的 `cs`（捷克语）。实际代码支持 11 种。

这样的文档错误一旦发生，处理捷克站点的 PDF 系统不会报错——它会用错误的 locale 去解析，然后输出**看起来正常但数字错位**的 Excel。

::: tip 文档是系统的一部分
在财务系统里尤其如此。文档错了，系统的行为就不可预期。

**规则：每次更新代码时同步更新文档；下次发布前先对一遍。**
:::

**这条规则适用于所有"代码—文档分离"的系统。**

## 七、安全设计清单

任何要操作真实业务数据的自动化脚本：

| 检查项 | 问题 |
| --- | --- |
| ✅ 默认配置 | 默认行为是写还是不写？ |
| ✅ dry-run 完整性 | dry-run 走完所有步骤了吗，还是只跳过了写操作？ |
| ✅ 幂等 | 重跑会怎样？有前置状态查询吗？ |
| ✅ 只读边界 | 能不能改成只读 + 输出报告？ |
| ✅ 路径安全 | 有外部输入参与路径拼接吗？ |
| ✅ 权限表现 | 无权限和无资源返回结果一致吗？ |
| ✅ 凭证 | 有硬编码吗？走环境变量吗？ |
| ✅ 数据模型隔离 | 敏感字段（价格等）有没有从公开模型里剔除？ |
| ✅ 防重复 | 有没有指纹/幂等键阻止重复处理？ |
| ✅ 留证 | 失败时有什么可用来还原现场？ |
| ✅ 文档一致性 | 文档描述和实际行为对得上吗？ |

## 八、一句话总结

> **自动化脚本的每一次写操作，都要假设"如果这一步错了会怎样"，然后让默认行为是最安全的那个。**

做对了，脚本出 bug 时损失的是一次空跑；做错了，损失的是客户的账。

::: tip 面试最爱问的一句话
> 「你的脚本要改真实业务数据，你怎么保证不出事？」

标准答案结构：

1. **默认 dry-run**，且 dry-run 走完整流程只在最后一步停住（暴露问题而非跳过问题）
2. **只读优先**，能输出差异报告就不自动修正
3. **幂等与指纹**，防止重复处理
4. **凭证走环境变量**，路径由服务端生成
5. **每项保护都有对应的测试和断言**，而不是口头约定
:::
